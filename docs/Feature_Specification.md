# Feature Specification - Version 1

Project: Private Mutual Connection Platform  
Version: 1.0  
Status: Draft for Engineering Implementation  
Audience: Product, Engineering, QA, DevOps, Architecture  
Last Updated: 2026-07-04

## 1. Purpose

This document defines the Version 1 feature specification for the privacy-first mutual connection platform. It translates the PRD, user journeys, architecture rules, and HLD chapters into implementable feature contracts for the core bounded contexts:

1. Authentication
2. User Profile
3. Social Graph Service
4. Private List
5. Matching Engine
6. Anonymous Chat
7. Reveal Service
8. Fair Play
9. Notification Service

The platform helps users discover mutual romantic interest among people they already know. It is not a stranger discovery product, swipe-based dating product, location-based dating product, or matrimonial platform.

## 2. Architectural Scope

Version 1 uses a microservices architecture with Spring Boot 3, Java 21, PostgreSQL, Spring Cloud Gateway, Flutter, JWT authentication, OTP login, REST APIs, and WebSocket chat.

### 2.1 Mandatory Architecture Rules

- Every business capability is implemented as an independently deployable microservice.
- Each service owns its own PostgreSQL database.
- Cross-service database access is prohibited.
- All client requests enter through the API Gateway.
- The API Gateway owns external routing, JWT validation, CORS policy, and rate limiting.
- Service-to-service communication uses REST in V1.
- Kafka and event streaming are deferred to V2, but services must remain event-ready.
- Social Graph Service is the only service allowed to import external connections.
- Matching depends only on mutual Private List inclusion.
- Matching must not consider user activity, paid status, engagement, popularity, or Fair Play score.
- Anonymous identity must remain protected until the automatic reveal deadline is reached.

### 2.2 Core Product Rules

- Every active user must maintain exactly 25 users in their Private List.
- A user may replace at most 3 Private List members per calendar day.
- Reordering Private List members is unlimited.
- Matching is processed in batches.
- Match notifications are delayed by a randomized interval.
- Anonymous chat starts only after a mutual match exists.
- Reveal timing is selected independently by both matched users at the beginning of the anonymous chat lifecycle.
- The system calculates an immutable reveal schedule from both selections and reveals identity automatically at the deadline.
- No feature may allow a user to infer another user's identity before reveal.

## 3. Shared API Standards

All public APIs must be exposed through the API Gateway using `/api/v1/{resource}` paths. Services may expose internal REST endpoints only on the private Docker network.

### 3.1 Common Headers

- `Authorization: Bearer <jwt>` for authenticated APIs.
- `X-Request-Id` generated by Gateway if absent.
- `X-Correlation-Id` propagated across all service calls.
- `Content-Type: application/json` for REST payloads.

### 3.2 Common Error Format

```json
{
  "code": "PRIVATE_LIST_SIZE_INVALID",
  "message": "Private List must contain exactly 25 users.",
  "details": {
    "requiredSize": 25,
    "actualSize": 23
  },
  "requestId": "7f3b9b0e-8e31-4d67-a9f5-5a39e9d47315",
  "timestamp": "2026-07-04T00:00:00Z"
}
```

### 3.3 Common Non-Functional Requirements

- P95 API latency for user-facing REST operations should be below 500 ms under expected V1 load, excluding external provider latency.
- All services must emit structured logs with request ID and correlation ID.
- All state-changing operations must be idempotent where retry is likely.
- All externally exposed request DTOs must be validated using Bean Validation.
- Services must return DTOs and must never expose persistence entities.
- All timestamps must be stored in UTC.
- All identifiers exposed externally must use UUIDs.
- All sensitive values must be excluded from logs.

# 4. Authentication

Service Owner: Identity Service  
Primary Database: Identity DB  
Primary Interfaces: REST via API Gateway  
Related ADRs: ADR-006, ADR-008

## 4.1 Purpose

Authentication verifies user ownership of a mobile number through OTP and issues JWT access credentials for authenticated access to platform APIs.

## 4.2 Business Goal

Reduce onboarding friction while maintaining strong identity assurance for a privacy-sensitive social product. Authentication must support trusted sessions without requiring passwords in V1.

## 4.3 User Story

As a new or returning user, I want to verify my mobile number using OTP so that I can securely access my account and maintain my private connections.

## 4.4 Functional Requirements

- The user can request an OTP by submitting a mobile number.
- The service must normalize mobile numbers into E.164 format before storage and comparison.
- The service must create a pending authentication challenge with a short expiration window.
- The service must send OTP through the configured SMS OTP provider.
- The user can verify the OTP before expiration.
- On successful OTP verification, the service must issue a signed JWT access token.
- The service must create an identity record for first-time users.
- The service must support returning users without duplicating identity records.
- The service must expose an endpoint for token validation to internal services if required.
- The service must support logout by invalidating refresh tokens or session records if refresh tokens are implemented in V1.
- The service must track failed OTP attempts and enforce lockout thresholds.

## 4.5 Non-Functional Requirements

- OTP generation must use a cryptographically secure random generator.
- OTP values must be stored hashed, never in plaintext.
- JWT signing keys must be managed through environment-based secrets, not source code.
- Authentication endpoints must be rate limited at the Gateway and service layer.
- OTP verification must complete within 300 ms excluding database latency.
- SMS provider failures must degrade gracefully with clear retry guidance.

## 4.6 Business Rules

- Phone OTP is the only V1 authentication mechanism.
- Users under 18 are outside V1 target scope and must not be onboarded if date-of-birth capture is enabled.
- A verified mobile number maps to exactly one identity.
- A user may request a limited number of OTPs per time window.
- A user may attempt a limited number of OTP verifications per challenge.
- Expired OTPs must not be accepted.

## 4.7 Validation Rules

- Mobile number is required.
- Mobile number must be valid for the selected country or already in E.164 format.
- OTP is required and must match the configured numeric length.
- OTP verification must reference the latest active challenge for the mobile number.
- Device metadata, if submitted, must pass length and format constraints.

## 4.8 API Requirements

Public endpoints:

- `POST /api/v1/auth/otp/request`
  - Request: `mobileNumber`, `countryCode`
  - Response: `challengeId`, `expiresAt`, `resendAvailableAt`
- `POST /api/v1/auth/otp/verify`
  - Request: `challengeId`, `otp`
  - Response: `accessToken`, `tokenType`, `expiresIn`, `userId`, `profileStatus`
- `POST /api/v1/auth/logout`
  - Authenticated.
  - Response: `204 No Content`
- `GET /api/v1/auth/me`
  - Authenticated.
  - Response: `userId`, `mobileNumberMasked`, `roles`, `profileStatus`

Internal endpoints:

- `GET /internal/v1/identities/{userId}`
  - Returns identity status for trusted service calls.

## 4.9 Database Impact

Identity DB must include:

- `identities`: `id`, `mobile_number_hash`, `mobile_number_encrypted`, `status`, `created_at`, `updated_at`
- `otp_challenges`: `id`, `identity_id`, `mobile_number_hash`, `otp_hash`, `expires_at`, `attempt_count`, `status`, `created_at`
- `sessions` or `refresh_tokens` if refresh token support is included.
- Unique index on normalized mobile number hash.
- Index on active OTP challenge by mobile number hash and status.

## 4.10 Dependencies

- API Gateway for routing, JWT validation, and rate limiting.
- SMS OTP provider.
- User Service for profile completion status after first login.
- PostgreSQL Identity DB.

## 4.11 Error Cases

- Invalid mobile number.
- OTP provider unavailable.
- OTP challenge expired.
- OTP verification failed.
- Too many OTP requests.
- Too many failed OTP attempts.
- Account disabled or restricted.
- JWT signing or key configuration failure.

## 4.12 Edge Cases

- User requests multiple OTPs in quick succession.
- User verifies an older OTP after a newer OTP was issued.
- SMS provider reports success but delivery is delayed.
- Same phone number is submitted in different formats.
- User changes device between OTP request and verification.

## 4.13 Security Considerations

- Store OTP hashes only.
- Encrypt mobile numbers at rest where lookup can be performed through deterministic hash.
- Never log OTP, JWT, full mobile number, or SMS provider secrets.
- Enforce replay protection for OTP challenges.
- Use short JWT expiration and secure signing algorithms.
- Gateway must reject expired, malformed, or unsigned tokens.

## 4.14 Future Enhancements

- Refresh token rotation.
- Device management.
- Account recovery workflows.
- Identity federation.
- Risk-based authentication.
- Web client support.

## 4.15 Acceptance Criteria

- A new user can request OTP, verify OTP, receive JWT, and proceed to profile creation.
- A returning user can authenticate with the same mobile number and receive the existing user identity.
- Expired OTPs are rejected.
- Rate limits are enforced for OTP request and verification.
- OTP and full phone number are not visible in application logs.
- All authenticated APIs reject requests without a valid JWT.

# 5. User Profile

Service Owner: User Service  
Primary Database: User DB  
Primary Interfaces: REST via API Gateway  
Related ADRs: ADR-001, ADR-002, ADR-007

## 5.1 Purpose

User Profile manages user-facing profile attributes, onboarding completion, privacy settings, and account lifecycle metadata.

## 5.2 Business Goal

Enable users to present enough information for post-reveal recognition while preventing identity leakage during anonymous matching and chat.

## 5.3 User Story

As a verified user, I want to create and manage my profile so that people can recognize me after automatic reveal while my identity remains hidden before reveal.

## 5.4 Functional Requirements

- The user must create a profile after successful authentication.
- Required V1 profile fields are display name and at least one profile photo if photo upload is available in V1.
- Optional fields may include bio, age/date of birth, gender, education, workplace, and interests based on product decisions.
- The service must track profile completion status.
- The service must expose the authenticated user's own full profile.
- The service must expose a restricted public profile only after successful reveal.
- Anonymous contexts must receive only anonymous alias metadata, never profile identity data.
- The service must support profile update operations.
- The service must support soft account deactivation.
- The service must not import contacts or external social relationships.

## 5.5 Non-Functional Requirements

- Profile reads should have P95 latency below 300 ms.
- Profile update APIs must be idempotent when the same payload is retried.
- Profile data must be versioned through `updated_at` for conflict handling.
- Uploaded media, if implemented, must be scanned or constrained by type and size.

## 5.6 Business Rules

- A user cannot create or save a Private List until mandatory profile setup is complete.
- Profile identity is hidden from matched users until Reveal Service confirms the automatic reveal has occurred.
- User Service owns profile data; other services must request profile summaries through APIs.
- Deactivated users must not be eligible for new matches.
- Existing anonymous chats involving a deactivated user must be blocked or marked unavailable.

## 5.7 Validation Rules

- Display name is required and must meet configured length limits.
- Bio must meet configured length limits and content rules.
- Date of birth, if collected, must indicate user is 18 or older.
- Profile photo, if collected, must be an approved MIME type and size.
- User settings must use known enum values.

## 5.8 API Requirements

Public endpoints:

- `POST /api/v1/users/profile`
  - Authenticated.
  - Creates profile for the authenticated user.
- `GET /api/v1/users/me`
  - Authenticated.
  - Returns full owner-visible profile.
- `PUT /api/v1/users/me`
  - Authenticated.
  - Updates profile fields.
- `GET /api/v1/users/{userId}/revealed-profile`
  - Authenticated.
  - Returns profile only if Reveal Service confirms automatic reveal completion.
- `POST /api/v1/users/me/deactivate`
  - Authenticated.
  - Soft deactivates account.

Internal endpoints:

- `GET /internal/v1/users/{userId}/status`
- `POST /internal/v1/users/profile-summaries`
  - Bulk lookup for service-owned workflows that are allowed to display revealed users.

## 5.9 Database Impact

User DB must include:

- `user_profiles`: `user_id`, `display_name`, `bio`, `date_of_birth`, `status`, `profile_completed`, `created_at`, `updated_at`
- `profile_photos`: `id`, `user_id`, `storage_key`, `display_order`, `status`, `created_at`
- `user_settings`: `user_id`, `notification_preferences`, `privacy_preferences`, `created_at`, `updated_at`
- Index on profile status.
- Unique primary key on `user_id`.

## 5.10 Dependencies

- Identity Service for authenticated user identity.
- Reveal Service for authorization to view revealed profiles.
- Notification Service for account lifecycle notification preferences.
- Object storage or local storage abstraction if profile photos are implemented.

## 5.11 Error Cases

- Profile already exists.
- Required field missing.
- Invalid profile photo.
- User is not authenticated.
- User is disabled.
- Revealed profile requested without reveal authorization.
- Concurrent profile update conflict.

## 5.12 Edge Cases

- User authenticates but exits before profile completion.
- User deletes or deactivates account while in another user's Private List.
- User changes display name after reveal.
- User updates profile while reveal schedule is pending or finalized.
- Profile photo processing succeeds after profile update response.

## 5.13 Security Considerations

- Never expose profile data in anonymous match or chat contexts.
- Enforce ownership on all profile update APIs.
- Sanitize free-text fields before rendering.
- Avoid logging bio or sensitive personal data.
- Use authorization checks for revealed profile access.

## 5.14 Future Enhancements

- Profile photo moderation.
- More detailed privacy controls.
- Profile verification.
- Multi-photo gallery.
- Account deletion and export workflows.

## 5.15 Acceptance Criteria

- A verified user can create, view, and update their own profile.
- A user cannot complete onboarding without mandatory profile fields.
- Anonymous chat and match APIs do not expose profile identity fields.
- Revealed profile data is returned only after automatic reveal completion.
- Deactivated users are excluded from new match eligibility.

# 6. Social Graph Service

Service Owner: Social Graph Service  
Primary Database: Social Graph DB  
Primary Interfaces: REST via API Gateway  
Related ADRs: ADR-004, ADR-009

## 6.1 Purpose

Social Graph Service imports, normalizes, stores, and resolves the user's known connections. In V1 the primary source is phone contacts. Future sources such as LinkedIn, Instagram, QR, and invite links must integrate only through this service.

## 6.2 Business Goal

Ensure users build Private Lists only from people they already know while keeping external integration complexity isolated from core business services.

## 6.3 User Story

As a user, I want the app to identify which of my contacts are registered users so that I can add known people to my Private List without searching strangers.

## 6.4 Functional Requirements

- The service must accept contact imports from the Flutter client after user permission is granted.
- The service must normalize imported phone numbers into a canonical format.
- The service must hash normalized contact identifiers for matching against registered users.
- The service must resolve imported contacts to registered platform users when possible.
- The service must expose eligible known connections for Private List selection.
- The service must not expose unregistered users as selectable Private List entries in V1.
- The service must support re-importing contacts and updating the graph.
- The service must deduplicate contacts within a user's graph.
- The service must store the source of every connection.
- The service must be designed with connector strategy interfaces for future providers.

## 6.5 Non-Functional Requirements

- Contact import must support batch payloads.
- Import processing must be idempotent for duplicate contact payloads.
- Contact matching must avoid storing unnecessary raw contact data.
- Bulk imports should be processed within acceptable mobile UX latency or return an async processing status.
- Connector logic must be isolated from domain graph logic.

## 6.6 Business Rules

- Social Graph Service is the only service allowed to process contacts or future social connectors.
- Private List Service must validate candidates through Social Graph Service.
- A user cannot add themselves to their own connection graph or Private List.
- Matching must not use graph strength, contact frequency, source count, or social proximity.
- External social provider data must not be shared with other services except as normalized eligible registered user IDs.

## 6.7 Validation Rules

- Import payload must contain a bounded number of contacts per request.
- Each contact must include at least one supported identifier, such as phone number in V1.
- Invalid phone numbers must be skipped or reported per item without failing the entire batch unless the payload is malformed.
- Duplicate contacts must be collapsed.
- Imported names from the device must not override registered user profiles.

## 6.8 API Requirements

Public endpoints:

- `POST /api/v1/social-graph/contacts/import`
  - Authenticated.
  - Request: contacts with local display name and phone numbers.
  - Response: `importId`, `status`, `registeredConnectionCount`
- `GET /api/v1/social-graph/connections`
  - Authenticated.
  - Returns registered known connections eligible for Private List selection.
- `GET /api/v1/social-graph/imports/{importId}`
  - Authenticated.
  - Returns import status and summary.
- `DELETE /api/v1/social-graph/connections/{connectionUserId}`
  - Optional V1 endpoint for removing a graph connection.

Internal endpoints:

- `POST /internal/v1/social-graph/validate-connections`
  - Request: owner user ID and candidate user IDs.
  - Response: validity per candidate.
- `GET /internal/v1/social-graph/users/{ownerUserId}/connections/{candidateUserId}`
  - Confirms known-connection relationship.

## 6.9 Database Impact

Social Graph DB must include:

- `contact_imports`: `id`, `user_id`, `status`, `total_count`, `valid_count`, `registered_count`, `created_at`, `completed_at`
- `graph_connections`: `id`, `user_id`, `connection_user_id`, `source`, `status`, `first_seen_at`, `last_seen_at`
- `imported_contact_identifiers`: `id`, `import_id`, `user_id`, `identifier_hash`, `identifier_type`, `matched_user_id`, `created_at`
- Unique index on `user_id`, `connection_user_id`, `source`.
- Index on identifier hash for matching.

## 6.10 Dependencies

- Identity Service for matching hashed mobile identifiers to registered identities.
- User Service for active user status.
- Private List Service for candidate validation.
- Mobile OS contacts permission through Flutter client.

## 6.11 Error Cases

- Contact permission not granted.
- Empty import payload.
- Payload exceeds allowed contact count.
- Identity resolution service unavailable.
- Contact import partially fails.
- Candidate not in user's social graph.

## 6.12 Edge Cases

- A contact joins after the user's import.
- A contact changes phone number.
- The same person appears under multiple device contacts.
- Two registered accounts map to conflicting identifiers, which must be prevented by Identity uniqueness.
- User imports contacts, then revokes device permission.

## 6.13 Security Considerations

- Store contact identifiers as hashes unless raw encrypted storage is explicitly required.
- Do not expose a user's contact book to other users.
- Do not expose whether an arbitrary phone number is registered outside the authenticated user's imported graph.
- Do not log raw phone numbers or imported contact names.
- Connector credentials must be isolated per provider.

## 6.14 Future Enhancements

- LinkedIn connector subject to platform policy.
- Instagram connector subject to platform policy.
- QR-based connection creation.
- Invite links.
- Connection confidence scoring for display only, not matching.

## 6.15 Acceptance Criteria

- A user can import contacts and receive registered known connections.
- Private List candidate validation succeeds only for known registered connections.
- Duplicate contacts do not create duplicate graph entries.
- Raw contact identifiers are not exposed through APIs or logs.
- No service other than Social Graph imports or processes contacts.

# 7. Private List

Service Owner: Private List Service  
Primary Database: Private List DB  
Primary Interfaces: REST via API Gateway  
Related ADRs: ADR-001, ADR-002, ADR-003

## 7.1 Purpose

Private List manages the user's curated list of exactly 25 known registered users. It is the core product primitive that drives mutual matching.

## 7.2 Business Goal

Create a trusted, intentional mechanism for users to express private interest without public exposure, rejection risk, or stranger discovery.

## 7.3 User Story

As a user, I want to maintain a private list of 25 people I know so that the platform can detect mutual interest without revealing my choices.

## 7.4 Functional Requirements

- The user must create a Private List with exactly 25 registered known connections.
- The user can view their own Private List.
- The user can reorder list members without daily limit.
- The user can replace up to 3 members per calendar day.
- The service must track replacement counts per user per day.
- The service must validate every member against Social Graph Service.
- The service must reject duplicate members.
- The service must reject the authenticated user as a member.
- The service must write an immutable change history for audit and match processing.
- The service must submit changed lists to the Matching Engine queue through REST in V1.

## 7.5 Non-Functional Requirements

- Private List save operations must be atomic within the service database.
- List validation must complete before persistence.
- Reorder-only operations must not increment replacement count.
- Writes must be idempotent when a client retries the same list version.
- Private List data must be treated as highly sensitive.

## 7.6 Business Rules

- Every active user must have exactly 25 list members.
- Maximum 3 replacements per calendar day.
- Unlimited reordering is allowed.
- Only registered users from the owner's Social Graph are eligible.
- Private List membership must never be exposed to other users.
- Private List order must not influence matching.
- Premium, activity, and engagement must not influence Private List validation or matching.

## 7.7 Validation Rules

- List size must equal 25.
- All member IDs must be valid UUIDs.
- All member IDs must be unique.
- Owner user ID must not appear in member IDs.
- Each member must be an active registered user.
- Each member must be a known connection according to Social Graph Service.
- Replacement count must not exceed remaining daily quota.
- Client-provided version must match current version if optimistic locking is used.

## 7.8 API Requirements

Public endpoints:

- `GET /api/v1/private-list`
  - Authenticated.
  - Returns owner-visible list with member IDs and display-safe summaries.
- `PUT /api/v1/private-list`
  - Authenticated.
  - Creates or replaces the full list.
  - Request: ordered array of 25 member user IDs and client version.
  - Response: list version, replacements used today, remaining replacements.
- `PATCH /api/v1/private-list/reorder`
  - Authenticated.
  - Reorders existing members only.
- `GET /api/v1/private-list/quota`
  - Authenticated.
  - Returns daily replacement quota state.

Internal endpoints:

- `GET /internal/v1/private-lists/{userId}/snapshot`
  - Used by Matching Engine.
- `GET /internal/v1/private-lists/changed-since`
  - Batch pull endpoint if queue handoff fails in V1.

## 7.9 Database Impact

Private List DB must include:

- `private_lists`: `id`, `user_id`, `version`, `status`, `created_at`, `updated_at`
- `private_list_members`: `id`, `list_id`, `member_user_id`, `position`, `created_at`
- `private_list_change_history`: `id`, `user_id`, `old_member_user_id`, `new_member_user_id`, `change_type`, `created_at`
- `daily_replacement_usage`: `id`, `user_id`, `usage_date`, `replacement_count`, `created_at`, `updated_at`
- Unique index on active list by `user_id`.
- Unique index on `list_id`, `member_user_id`.
- Index on daily quota by `user_id`, `usage_date`.

## 7.10 Dependencies

- Social Graph Service for candidate validation.
- User Service for active user status and owner-visible summaries.
- Matching Service for match queue submission.
- API Gateway for authentication and rate limiting.

## 7.11 Error Cases

- List contains fewer or more than 25 members.
- Duplicate member IDs.
- Member is not a known connection.
- Member is inactive or deleted.
- Daily replacement quota exceeded.
- Concurrent list update conflict.
- Matching queue submission fails after list persistence.

## 7.12 Edge Cases

- User reorders and replaces in the same request.
- A member deactivates after being added.
- User imports contacts after failing candidate validation.
- A save request is retried after a network timeout.
- Calendar day changes during replacement calculation.

## 7.13 Security Considerations

- Private List membership must be visible only to the owner and authorized internal matching workflows.
- Do not include Private List member IDs in analytics events visible outside trusted systems.
- Mask or omit list contents from logs.
- Enforce authorization by authenticated principal, not request body user ID.
- Avoid APIs that reveal whether a specific user has added the caller.

## 7.14 Future Enhancements

- Pause matching.
- Private List backups or restore.
- Improved replacement UX.
- Differential privacy for aggregate metrics.
- Event-driven list update publishing through Kafka.

## 7.15 Acceptance Criteria

- A user can save a Private List only when it contains exactly 25 valid known registered users.
- A user can reorder the list any number of times without consuming replacement quota.
- A user cannot replace more than 3 members in a calendar day.
- Private List updates are submitted for batch matching.
- No API reveals another user's Private List membership.

# 8. Matching Engine

Service Owner: Matching Service  
Primary Database: Matching DB  
Primary Interfaces: Internal REST, scheduler, public match read APIs  
Related ADRs: ADR-005

## 8.1 Purpose

Matching Engine detects mutual Private List inclusion and creates anonymous matches through batch processing.

## 8.2 Business Goal

Safely identify mutual romantic interest while preserving anonymity, preventing inference attacks, and ensuring matching fairness.

## 8.3 User Story

As a user, I want the platform to notify me when someone I privately selected also selected me, without exposing either person's identity too early.

## 8.4 Functional Requirements

- The service must process Private List updates in batches.
- The service must detect mutual inclusion: user A lists user B and user B lists user A.
- The service must create exactly one active match record for each mutually matched pair.
- The service must not create duplicate active matches.
- The service must assign anonymous participant aliases for match/chat contexts.
- The service must request delayed notification scheduling after match creation.
- The service must expose the authenticated user's anonymous matches.
- The service must update match status when chat, reveal, block, or deactivation workflows require it.
- The service must not use list order, activity, popularity, premium status, Fair Play score, or engagement data to influence matching.

## 8.5 Non-Functional Requirements

- Batch jobs must be idempotent.
- Match creation must be transactional per pair.
- Batch processing must tolerate partial failures and resume safely.
- Matching logic must be deterministic for the same input snapshot.
- Matching must be observable through job metrics, failure counts, and duration.

## 8.6 Business Rules

- Matching depends only on mutual Private List inclusion.
- Matching is processed in batches, not immediate direct response to user save.
- Notifications must be delayed using randomized timing.
- Identity must remain anonymous after match creation.
- Existing matches remain valid unless business policy explicitly ends them.
- Fair Play score may restrict platform access but must not rank or prioritize matching.

## 8.7 Validation Rules

- Both users must be active.
- Both users must have active Private Lists.
- Both lists must contain exactly 25 members.
- Match pair must be canonicalized so `(A, B)` and `(B, A)` are the same pair.
- Existing active or revealed match must be checked before creation.

## 8.8 API Requirements

Public endpoints:

- `GET /api/v1/matches`
  - Authenticated.
  - Returns anonymous matches for current user.
- `GET /api/v1/matches/{matchId}`
  - Authenticated.
  - Returns anonymous match details if user is a participant.

Internal endpoints:

- `POST /internal/v1/matching/queue-list-update`
  - Called by Private List Service after list change.
- `POST /internal/v1/matching/jobs/run`
  - Optional operational endpoint protected from public access.
- `PATCH /internal/v1/matches/{matchId}/status`
  - Used by Chat, Reveal, Fair Play, or User lifecycle workflows.

Scheduled job:

- `private-list-match-batch`
  - Runs at configured interval.
  - Pulls queued list updates or changed list snapshots.
  - Creates anonymous matches.
  - Schedules notifications.

## 8.9 Database Impact

Matching DB must include:

- `match_jobs`: `id`, `status`, `started_at`, `completed_at`, `processed_count`, `failure_count`
- `match_queue_items`: `id`, `user_id`, `private_list_version`, `status`, `created_at`, `processed_at`
- `matches`: `id`, `user_a_id`, `user_b_id`, `status`, `created_at`, `updated_at`
- `match_participants`: `id`, `match_id`, `user_id`, `anonymous_alias`, `notification_status`, `created_at`
- Unique canonical pair index on active matches.
- Index on participant user ID for match listing.

## 8.10 Dependencies

- Private List Service for snapshots.
- User Service for active user status.
- Notification Service for delayed match notifications.
- Chat Service for conversation initialization or lazy chat creation.
- Reveal Service for status transitions.

## 8.11 Error Cases

- Private List snapshot unavailable.
- User deactivated during batch processing.
- Duplicate match detected.
- Notification scheduling unavailable.
- Batch job crashes mid-run.

# 10. Reveal Service

Service Owner: Reveal Service  
Primary Database: Reveal DB  
Primary Interfaces: REST via API Gateway  

## 10.1 Purpose

Reveal Service manages the canonical V1 identity reveal lifecycle for matched users:

- Initial reveal-duration preference collection at the beginning of anonymous chat.
- Reveal schedule calculation after both participants submit valid selections.
- Persistence of an immutable UTC `revealAt` timestamp.
- Automatic identity reveal when the deadline is reached.

Reveal Service does not manage reveal requests, reveal approvals, reveal rejections, or any later mutual-consent workflow in V1.

## 10.2 Business Goal

Balance user preference, fairness between both participants, predictable anonymity, and guaranteed eventual identity reveal. Each user can express how long they prefer to remain anonymous, the arithmetic mean creates a neutral system-calculated schedule, and both users receive the same automatic reveal outcome without later pressure or negotiation.

## 10.3 User Story

- As a matched user, I want to select 3, 5, or 7 days of anonymity when I first enter a new anonymous chat so that I can express my comfort level before conversation starts.
- As a matched user, I want the system to calculate and show the final reveal schedule only after both of us have submitted choices so that neither participant can influence the other.
- As a matched user, I want my identity to remain hidden until the reveal deadline so that anonymous chat privacy is preserved.
- As a matched user, I want identity reveal to happen automatically at the deadline so that reveal is predictable and not dependent on later consent.

## 10.4 Functional Requirements

- When Matching Service creates a mutual match, Chat Service must create or initialize an anonymous chat for the matched pair.
- When a participant first enters the newly created anonymous chat, the client must show a mandatory modal asking: "How long would you like to remain anonymous?"
- The allowed selections are exactly 3 days, 5 days, and 7 days.
- Each participant must submit one selection independently before seeing the other participant's selection or any final schedule derived from it.
- The service must reject attempts to retrieve the counterpart's individual selection.
- The service must wait until both participants have submitted valid selections.
- After the second valid selection is received, the service must calculate `revealPeriodDays = (userASelectionDays + userBSelectionDays) / 2`.
- The service must support the complete calculation matrix:
  - 3 and 3 -> reveal after 3 days.
  - 3 and 5 -> reveal after 4 days.
  - 3 and 7 -> reveal after 5 days.
  - 5 and 5 -> reveal after 5 days.
  - 5 and 7 -> reveal after 6 days.
  - 7 and 7 -> reveal after 7 days.
- Because allowed values are exactly 3, 5, and 7, the arithmetic mean is always a whole number.
- The service must define `revealScheduleStartAt` as the UTC timestamp when both valid reveal-duration selections have been received and the schedule is finalized.
- The service must calculate and persist `revealAt = revealScheduleStartAt + revealPeriodDays`.
- The calculated `revealAt` timestamp must be immutable in V1.
- After schedule finalization, neither participant can cancel the reveal, postpone the reveal, request early reveal, decline the reveal, change their original duration choice, or reset the reveal timer.
- Reaching `revealAt` is sufficient to trigger automatic identity reveal.
- At `revealAt`, the service must automatically transition the match reveal state so both participants can access each other's real identity according to the platform's reveal rules.
- The service must expose reveal status and the final system-calculated reveal date/time or countdown after schedule finalization.
- The service must notify both participants when the reveal schedule is finalized.
- The service must notify both participants when identity reveal has occurred.
- The service must authorize User Service to return revealed profiles only after automatic reveal completion.
- The service must maintain an auditable history of participant selections, selection timestamps, schedule finalization timestamp, calculated reveal period, calculated `revealAt`, and automatic reveal completion timestamp.

## 10.5 Non-Functional Requirements

- Reveal schedule finalization must be transactional so both selections, calculated period, `revealScheduleStartAt`, and `revealAt` are persisted consistently.
- All reveal timing calculations must use server-side UTC time.
- Repeated selection submissions and automatic reveal processing must be idempotent.
- Reveal selection, schedule finalization, and automatic reveal completion must be auditable.
- Automatic reveal workers must be reliable across retries, duplicate execution, and service restarts.
- No identity information may become accessible before the exact `revealAt` timestamp.
- The service must not trust client clocks for reveal timing or schedule calculation.
- Reveal status reads should have P95 latency below 300 ms.

## 10.6 Business Rules

- Choices are exactly 3, 5, or 7 days.
- Both users choose independently.
- Individual choices remain private from the other participant.
- User A must not be able to see User B's selection before submitting their own choice.
- User B must not be able to see User A's selection before submitting their own choice.
- The arithmetic mean of both selections determines `revealPeriodDays`.
- The reveal schedule starts when the second valid selection is received and the schedule is finalized.
- `revealAt` is immutable after schedule finalization.
- Reveal is automatic at `revealAt`.
- There is no later consent, reveal request, approval, rejection, accept action, or decline action in V1.
- Reveal cannot occur before the exact `revealAt` timestamp.
- Once automatic reveal completes, the reveal state is irreversible in V1.
- Reveal applies to a match pair, not globally to all contexts.

## 10.7 Validation Rules

- Match ID is required and must be a valid UUID.
- Authenticated user must be a participant in the match.
- Match must be active.
- Duration choice must be exactly 3, 5, or 7 days.
- Each participant can submit only once per match.
- Submitted choices cannot be changed.
- Schedule finalization can occur only after both participant selections exist.
- Automatic reveal can complete only when server-side UTC time is greater than or equal to `revealAt`.
- User cannot submit a selection on behalf of the other participant.

## 10.8 API Requirements

Public endpoints:

- `GET /api/v1/reveals/matches/{matchId}`
  - Authenticated.
  - Returns current reveal status, whether the authenticated participant has submitted their selection, whether the schedule is finalized, calculated `revealPeriodDays`, `revealScheduleStartAt`, `revealAt`, `revealedAt`, and display-safe countdown data when available.
  - Must not return the other participant's individual selection.
- `POST /api/v1/reveals/matches/{matchId}/duration-selection`
  - Authenticated.
  - Request: `durationDays`.
  - Response: participant submission status and, when both selections now exist, finalized reveal schedule.

The public API must not include endpoints for request reveal, accept reveal, decline reveal, cancel reveal, postpone reveal, early reveal, or reveal reset.

Internal endpoints:

- `GET /internal/v1/reveals/matches/{matchId}/authorization`
  - Used by User Service to authorize revealed profile access after automatic reveal completion.
- `GET /internal/v1/reveals/users/{requesterId}/can-view/{targetUserId}`
  - Optional direct authorization endpoint.
- `POST /internal/v1/reveals/process-due`
  - Optional worker endpoint or job trigger for idempotent automatic reveal processing.

## 10.9 Database Impact

Reveal DB must conceptually support:

- Match ID.
- Participant A user ID and participant B user ID.
- Participant A selection in days.
- Participant B selection in days.
- Participant A selection timestamp.
- Participant B selection timestamp.
- Schedule finalization timestamp.
- Calculated reveal period in days.
- Immutable `revealAt` timestamp.
- Reveal status, such as awaiting selections, scheduled, revealed, or unavailable due to match lifecycle.
- Automatic reveal completion timestamp `revealedAt`.
- Audit metadata, including created/updated timestamps, source request IDs, correlation IDs, and idempotency keys where applicable.
- Uniqueness constraints that prevent more than one selection per participant per match.
- Indexing for due automatic reveals by status and `revealAt`.

This section defines conceptual data requirements only. Physical schema names and normalization choices belong in detailed database design.

## 10.10 Dependencies

- Matching Service for match status and participant validation.
- Chat Service for anonymous chat initialization, mandatory duration-selection gating, and identity display updates after reveal.
- User Service for revealed profile display and post-reveal authorization checks.
- Notification Service for schedule-finalized and identity-revealed notifications.

## 10.11 Error Cases

- Match not found.
- User is not a match participant.
- Match is inactive.
- Invalid duration.
- Duplicate selection submission.
- Attempt to change a submitted selection.
- Attempt to view the other participant's individual selection.
- Automatic reveal attempted before `revealAt`.
- Scheduler retry after transient failure.
- Reveal already completed.
- Notification scheduling failure.

## 10.12 Edge Cases

- One participant submits much later than the other; the schedule remains pending until the second valid selection is received.
- One participant never submits; OPEN PRODUCT QUESTION: V1 does not yet define timeout, reminder, fallback, or match-expiration behavior for this case.
- App is offline when reveal occurs; reveal state is authoritative server-side and the client must sync status on reconnect.
- Automatic reveal worker retries after transient failure; processing must be idempotent.
- Service restarts near `revealAt`; persisted due reveal records must be processed after recovery.
- Duplicate scheduled execution occurs; only one reveal completion timestamp should be recorded.
- User account is suspended or deleted before reveal; Reveal Service must coordinate with User Service and Fair Play policy before exposing identity.
- Reveal occurs while users are actively chatting; Chat Service must refresh identity display only after Reveal Service confirms completion.
- User Service is temporarily unavailable at reveal time; reveal state remains completed and profile access can succeed after User Service recovery.

## 10.13 Security Considerations

- Hide individual duration selections from the other participant.
- Use server-authoritative UTC time for all reveal calculations.
- Prevent client clock manipulation by ignoring client-provided timestamps.
- Prevent early profile access before the exact `revealAt` timestamp and automatic reveal completion.
- Enforce participant authorization on every reveal operation.
- User Service must verify reveal authorization after automatic reveal before returning profile identity.
- Persist audit logs for selections, schedule finalization, worker execution, and reveal completion.
- Do not include identity data or individual selections in pre-reveal notifications, chat payloads, logs, or analytics events.

## 10.14 Acceptance Criteria

- Given User A selects 3 days and User B selects 3 days, when the second valid selection is received, then `revealPeriodDays` is 3 and `revealAt` is `revealScheduleStartAt + 3 days`.
- Given User A selects 3 days and User B selects 5 days, when the second valid selection is received, then `revealPeriodDays` is 4 and `revealAt` is `revealScheduleStartAt + 4 days`.
- Given User A selects 3 days and User B selects 7 days, when the second valid selection is received, then `revealPeriodDays` is 5 and `revealAt` is `revealScheduleStartAt + 5 days`.
- Given User A selects 5 days and User B selects 5 days, when the second valid selection is received, then `revealPeriodDays` is 5 and `revealAt` is `revealScheduleStartAt + 5 days`.
- Given User A selects 5 days and User B selects 7 days, when the second valid selection is received, then `revealPeriodDays` is 6 and `revealAt` is `revealScheduleStartAt + 6 days`.
- Given User A selects 7 days and User B selects 7 days, when the second valid selection is received, then `revealPeriodDays` is 7 and `revealAt` is `revealScheduleStartAt + 7 days`.
- Given only one participant has submitted a duration, when either participant retrieves reveal status, then the final schedule is not shown and the other participant's individual selection is not exposed.
- Given both participants have submitted valid durations, when the schedule is finalized, then both participants are notified that the reveal schedule has been finalized.
- Given the current server-side UTC time is before `revealAt`, when either participant requests the other user's profile, then User Service must not return identity data.
- Given the current server-side UTC time is equal to or after `revealAt`, when automatic reveal processing runs, then Reveal Service marks the match revealed and records `revealedAt`.
- Given automatic reveal completes, when profile authorization is checked, then User Service may return the counterpart's revealed profile according to product rules.
- Given a participant repeats the same duration submission after a successful submission, when the request is processed, then the operation is idempotent and does not create a second selection or change the original timestamp.
- Given a participant submits a different duration after a successful submission, when the request is processed, then the service rejects the change.
- Given automatic reveal processing runs more than once for the same due match, when retries or duplicate executions occur, then only one reveal completion is persisted and notifications are not duplicated beyond idempotency policy.
- Given a client submits local time data with the selection, when Reveal Service calculates the schedule, then client time is ignored and server-side UTC is used.

## 10.15 Future Enhancements

- Reminder policy for participants who have not submitted a duration selection.
- Product-defined timeout or fallback policy when one participant never submits.
- Configurable duration options only if approved by privacy and product review.
- Post-reveal safety controls.
- Partial reveal concepts, if approved by privacy review.
- Reveal revocation policy for future legal/privacy requirements.

10. User lands on Home Dashboard.

## 13.2 Private List Update and Match Creation

1. User updates or reorders Private List.
2. Private List Service validates exactly 25 members.
3. Private List Service validates candidates through Social Graph Service.
4. Private List Service enforces replacement quota.
5. Private List Service persists list version and change history.
6. Matching Service queues the changed list.
7. Batch job evaluates mutual inclusion.
8. Matching Service creates anonymous match if mutual inclusion exists.
9. Notification Service schedules randomized delayed match notification.
10. Chat Service initializes chat or creates it lazily on first open.

## 13.3 Anonymous Chat and Reveal

1. User opens anonymous match.
2. Chat Service authorizes participant access.
3. Users exchange anonymous messages.
4. Either user reports violations through Fair Play.
5. Each participant selects 3, 5, or 7 days from the mandatory reveal-duration modal before normal chat use.
6. Reveal Service keeps individual selections private and waits for both valid submissions.
7. After the second selection, Reveal Service calculates the arithmetic mean, finalizes `revealScheduleStartAt`, and persists immutable `revealAt`.
8. Users exchange anonymous messages until the exact `revealAt` timestamp.
9. At `revealAt`, Reveal Service automatically records revealed match state.
10. User Service exposes revealed profile through authorized APIs.

## 13.4 Fair Play Enforcement

1. User reports a message, match, or user.
2. Fair Play Service validates reporter context.
3. Fair Play Service records report and evidence references.
4. Policy evaluation updates score and restrictions.
5. Notification Service sends warning or restriction notice when applicable.
6. Chat, Reveal, or other services enforce restriction status.

- Reveal duration-selection, schedule calculation, and automatic reveal lifecycle are covered by unit tests.

- Social Graph import normalization is covered by unit tests.

- Notification randomized delay and privacy-safe templates are covered by tests.
