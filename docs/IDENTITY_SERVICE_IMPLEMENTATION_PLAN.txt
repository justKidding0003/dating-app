5. Proposed API Contracts
-------------------------

Base path:

/api/v1/auth

POST /api/v1/auth/otp/request

Request:

{
  "phoneNumber": "+919876543210",
  "countryCode": "IN"
}

Response: 202 Accepted

{
  "challengeId": "uuid",
  "expiresAt": "2026-07-05T12:00:00Z",
  "resendAvailableAt": "2026-07-05T11:59:00Z"
}

Validation:

- phoneNumber is required.
- E.164 accepted directly.
- Otherwise normalize using countryCode.
- countryCode must be ISO-3166 alpha-2 when needed.
- Never reveal account existence.

POST /api/v1/auth/otp/verify

Request:

{
  "challengeId": "uuid",
  "otp": "123456",
  "deviceName": "Pixel 8",
  "deviceId": "optional-client-device-id"
}

Response: 200 OK

{
  "accessToken": "jwt",
  "refreshToken": "opaque-token",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "identityId": "uuid"
}

Validation:

- challengeId is required and must be a UUID.
- otp is required, numeric, and must match configured length.
- Device metadata is optional and length-bounded.

POST /api/v1/auth/token/refresh

Request:

{
  "refreshToken": "opaque-token"
}

Response: 200 OK

{
  "accessToken": "jwt",
  "refreshToken": "new-opaque-token",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "identityId": "uuid"
}

Behavior:

- Rotates refresh token.
- Revokes old session token.
- Detects reuse where possible and revokes token family/session.

POST /api/v1/auth/logout

Request:

{
  "refreshToken": "opaque-token"
}

Response:

204 No Content

Common error format:

{
  "code": "OTP_INVALID",
  "message": "The OTP could not be verified.",
  "details": {},
  "requestId": "uuid",
  "timestamp": "2026-07-05T00:00:00Z"
}

Likely status codes:

- 400 Bad Request: validation, invalid phone, invalid OTP format.
- 401 Unauthorized: invalid access token or refresh token.
- 403 Forbidden: disabled identity.
- 409 Conflict: consumed challenge or rotated-token reuse if exposed generically.
- 422 Unprocessable Entity: expired or invalid challenge.
- 429 Too Many Requests: OTP request/resend/verification throttled.
- 503 Service Unavailable: OTP delivery provider unavailable.


6. Proposed Database Model
--------------------------

identities:

- id uuid primary key
- phone_number_hash varchar(128) not null unique
- phone_number_encrypted text null/optional for V1 if encryption key configured
- status varchar(32) not null
- created_at timestamptz not null
- updated_at timestamptz not null

otp_challenges:

- id uuid primary key
- identity_id uuid null references identities(id)
- phone_number_hash varchar(128) not null
- otp_hash varchar(255) not null
- status varchar(32) not null
- expires_at timestamptz not null
- resend_available_at timestamptz not null
- attempt_count int not null
- max_attempts int not null
- created_at timestamptz not null
- verified_at timestamptz null
- consumed_at timestamptz null

Indexes:

- idx_otp_challenges_phone_status_created_at
- idx_otp_challenges_expires_at

refresh_sessions:

- id uuid primary key
- identity_id uuid not null references identities(id)
- refresh_token_hash varchar(255) not null unique

- status varchar(32) not null
- expires_at timestamptz not null
- revoked_at timestamptz null
- rotated_at timestamptz null
- reuse_detected_at timestamptz null
- device_id varchar(128) null

- idx_refresh_sessions_identity_status

No tables should be created for profile, contacts, private list, graph, matching,
chat, reveal, or reputation.


7. Security Decisions
---------------------

- OTP generated with SecureRandom.
- OTP stored only as BCrypt/Argon2-style secure hash, never raw.
- Refresh token generated as high-entropy opaque random value.
- Refresh token stored only as secure hash.
- Access token is JWT, short-lived, with no phone number or sensitive PII in
  claims.
- JWT claims should be minimal: sub as identityId, iss, iat, exp, and minimal
  roles/scope if needed.
- JWT secret/signing key comes only from configuration or environment variables.
- Phone lookup uses deterministic HMAC hash of normalized E.164 phone number with
  environment-provided pepper.
- Full phone number must not be logged.
- Development OTP provider is active only under local/dev profile.
- Development provider may log OTP only in controlled local logs, never API
  responses and never production.
- Production profile must fail startup unless secure JWT and phone hash secrets
  are configured.
- Service-level rate limiting is implemented in-memory for V1 foundation.
- Gateway rate limiting remains required later.
- All timestamps are stored in UTC.
- Correlation/request IDs are propagated in logs and error responses.

- Recommendation: add Testcontainers if Docker is expected in CI/local. Otherwise
  use focused unit tests now and add Testcontainers when CI is established.


9. Testing Plan
---------------

Unit tests:

- OTP generation length, numeric format, and secure randomness boundaries.
- OTP request creates challenge with hashed OTP.
- OTP request respects resend/request rate limits.
- Valid OTP consumes challenge and issues tokens.
- Invalid OTP increments attempts.
- Expired OTP is rejected.
- Max attempt limit locks challenge.
- Consumed OTP cannot be reused.
- Phone normalization returns stable E.164.
- Refresh token rotation revokes/replaces previous token.
- Reuse of rotated/revoked refresh token is detected.
- Logout revokes refresh session.
- JWT contains only approved minimal claims.

Integration tests:

- Controller validation and status codes.
- Security allows auth endpoints and protects authenticated endpoints.
- Flyway migration applies.
- JPA mappings validate against schema.
- Global error response shape includes request ID and timestamp.


10. Risks And Open Questions
----------------------------

Conflicts or documentation tension:

- The task requires refresh token lifecycle in V1, while Feature_Specification.md
  lists refresh token rotation under future enhancements. Proposed resolution:
  follow the task and implement refresh tokens now because the requested endpoints
  explicitly include refresh.
- Documentation says Gateway owns JWT validation and rate limiting, but the task
  also requires service-layer rate limiting. Proposed resolution: implement
  service-level baseline now and keep Gateway rate limiting as an architecture
  requirement.
- Feature_Specification.md includes GET /api/v1/auth/me and internal identity
  lookup, but the task minimum endpoints do not. Proposed resolution: defer those
  unless explicitly requested for this first implementation.
- Feature_Specification.md OTP verify response mentions userId and profileStatus;
  this service must not own profile. Proposed resolution: return identityId only,
  or return profileStatus as UNKNOWN/PROFILE_REQUIRED only if explicitly approved.
- Current DB config conflicts with Docker Compose credentials.
- Production phone-number encryption needs a key-management decision. For V1,
  deterministic HMAC hash is required for lookup; encrypted storage can be
  implemented with an environment key or deferred if not needed by any V1 API.
- Local dev OTP visibility must be useful but not leak through API responses.
  Proposed resolution: log only under local profile with masked phone and
  challenge ID.

Open questions:

- Should the first implementation include GET /api/v1/auth/me?
- Should verify response use identityId or keep docs-compatible userId naming?
- Should Testcontainers be added now?
- Should the Maven artifact be renamed to identity-service in this change?
